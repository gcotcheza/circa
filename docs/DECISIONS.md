# Decisions

The engineering *why*: how this repository is built, gated and kept honest, when
the reason is too long to live in a comment. It is a different file from
`docs/rationale-app.md`, `docs/rationale-data.md` and
`docs/rationale-frontend.md` on purpose — those hold the domain and code
rationale, why a rollup is recomputed the way it is or why a prompt is shaped
the way it is, and the code points into them with `See docs/rationale-x.md §
"Heading"`. This file holds process decisions, which no line of application code
points at.

---

### the-gate-checks-dependency-advisories
`composer audit --locked --no-dev` and `npm audit --omit=dev --audit-level=high` are `scripts/ci.sh`'s advisory checks, and they sit in two different places on purpose. The composer half is inside the container block, directly after Pint: `--locked` reads `composer.lock` rather than the installed tree, so it is seconds of parsing plus one advisory lookup and belongs among the cheap checks. The npm half sits immediately before ESLint, in the front-end block that runs before the stack exists at all — it is the first step that needs `node_modules`, and pairing it with the composer half would put a cold `npm ci` ahead of a 90-second phpstan run for no gain.

Both are scoped to what production actually installs. `--no-dev` and `--omit=dev` keep phpunit, pint, larastan, vite and eslint out of the result: an advisory against a package no user can be reached through would redden the gate for something unfixable-by-design and teach people to skip the step.

ABANDONMENT IS REPORTED, NOT FAILED. `composer audit`'s own default for an abandoned package is `fail` (`composer config audit.abandoned` answers `fail`; composer 2.10 here), and an abandoned package is not a vulnerability: nobody can fix it the afternoon it is announced, because the fix is choosing a replacement library. Left at the default, the first abandonment in the production `require` block would redden every branch on the repository under a message that says "advisory", which is both false and unactionable — and a gate that is red for a reason nobody can clear is a gate people learn to skip. So the call carries `--abandoned=report`: the abandonment is printed where the next person reading the gate output will see it, and the run continues. The stricter setting exists and was declined deliberately; `--abandoned=fail` is one word away for whoever decides the noise is worth it.

THE TWO SEVERITY DIALS ARE NOT THE SAME, and the difference is narrower than it looks. npm takes a floor: `--audit-level=high` passes anything below High. Composer has no floor — `composer audit --help` offers `--ignore-severity`, which is an ignore-LIST of named levels, not a minimum — so short of enumerating every severity we do not care about, it fails on any advisory it finds against a production package. We leave it there deliberately: it is stricter rather than looser, and this project's production `require` block is short enough that the noise is affordable. If that stops being true, the honest change is an explicit `--ignore-severity` line with a reason beside it, never dropping the step.

The guard in front of the npm step is `[ -d node_modules ] || npm ci … && npm audit …`, with `&&` and not `;`. The shell reads it as `(test || install) && audit`: a warm tree skips the install and audits, a cold tree installs and then audits, and an install that fails stops the step instead of running the audit against half a tree. On a warm worktree these are the gate steps that need the network; a cold checkout also needs it for `composer install`, for the guarded `npm ci` beside the audit, and for the image build itself. Either way a Packagist or npm registry outage can hold up a merge. That is the accepted cost of not learning about a known vulnerability from somewhere other than the gate.

### the-browsers-copy-of-the-rules-is-generated-and-gated
Inline validation means the validation rules exist twice: once in `app/Http/Requests`, where they are enforced, and once in the browser, where they are only ever said out loud. The owner chose that shape deliberately over the alternative — Precognition, which asks the server to validate one field per blur — because it costs a round trip per box on a phone, and because a form that goes quiet when the connection does is worse than one that never spoke. What follows is how the second copy is kept from becoming a lie.

IT IS GENERATED, AND THE GENERATOR REFUSES TO GUESS. `php artisan validation:export` walks the FormRequests through the real `Illuminate\Validation\Validator` and writes `resources/js/lib/validation/rules.generated.json` — rules, resolved parameters (ceilings arrive as the numbers `config/health.php` currently holds, never as a second copy of the limit) and the exact sentence Laravel's own message lookup produces. Reaching into that lookup, through one `ReflectionMethod` on a protected method, was chosen over reimplementing it: the ordering it encodes — a custom `messages()` line beating the generic one, a wildcard key matching a concrete attribute, `max` on a numeric field reading differently from `max` on a string — is precisely the sort of thing a second implementation gets 95% right, and the 5% is a sentence nobody notices is wrong. A rule the exporter does not recognise is a non-zero exit with the rule named, never a silent omission, because a rule missing from the export is a box the browser calls fine and the server refuses.

THE COST IS BOUNDED BY TWO TESTS THAT FAIL THE GATE, not by discipline. `tests/Feature/Validation/RulesAgreementTest.php` regenerates the artifacts and compares them byte for byte, so a moved ceiling or a reworded sentence turns the gate red until `validation:export` is re-run — the drift is caught the same afternoon it is introduced rather than discovered in a screenshot. `tests/js/validation-agreement.test.js` is the other half and the more interesting one: the exporter also writes ~2000 `(request, field, value)` cases whose answers come from RUNNING the real validator, and the browser evaluator must return the identical sentence for every case. The cases are derived from the rules, so a new rule generates its own cases and nobody has to remember to write them. Neither test is redundant — the first proves the artifact matches the server, the second proves the evaluator matches the artifact, and drift can enter at either seam.

WHAT THE BROWSER DECLINES TO ANSWER is as much of the design as what it answers. `exists`, `unique`, `current_password`, `Password::uncompromised()`, `email` and every date rule are exported as `server_only` with no sentence attached, because each needs a database, a session, a breach corpus or PHP's date parser against a clock in a timezone the phone may not be in. The browser says nothing about them and the 422 says it after submit, exactly as before. That asymmetry is deliberate and one-directional: being silent where the server would refuse costs a round trip, while refusing where the server would accept costs the reader's trust in every other refusal. `RulesAgreementTest` additionally asserts that no mirrored rule ever sits behind a server-only one in a field's rule list, which is what makes "the browser's sentence is the server's headline sentence" a property rather than a hope.

THE LOGIN RULES MOVED INTO A CONSTANT and stayed in the controller. `LoginController::RULES` is read by the exporter; lifting the two lines into a FormRequest would have been tidier to look at and would have changed where a refused login redirects, which is not a thing to change while adding inline validation to the box above it. `RulesAgreementTest` names the three remaining inline `validate()` call sites — login, the meal-memory search box, the browser's own error reporter — and fails when a fourth appears, so a new form cannot quietly acquire rules the browser was never taught.

The native-constraint cleanup rode along in the same change because it is the same decision seen from the other side. `required`, `maxlength` and `pattern` were the browser refusing in wording this app did not write, unstyled, gone on the next tap, and on iOS sometimes refusing a submit while drawing nothing at all — the bug `DecimalInputTest` was written for. Every `<form>` now carries `novalidate`, no input carries a veto, and the sentence that stands in for each of them is the server's own. The `:max` bounds left on the calendar components are not vetoes: Air Datepicker greys the day out rather than refusing it, and `DatePickerNullBoundsTest` pins them deliberately.
